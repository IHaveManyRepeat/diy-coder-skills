## 第 1 步 —— 组件清单与分层（源 step-03 第 1、3 指令）

**先说清为什么**：讲清「为什么组件要逐条写职责而不是画个框」——框没有职责边界，问题一来就说不清该改哪。用你自己的话讲。

### 1.1 组件清单（源 step-03 第 1 指令）

逐条落 `components[]`——每条问四句：**它的职责是什么** / **它暴露什么**（公开 API、导出）/ **它封装什么**（内部细节）/ **它多大**（文件数、行数、复杂度）。记录键：

```yaml
- {id: AN-01, name: <模块名>, layer: 展示层|应用层|领域层|基础设施层|未分层,
   responsibility: <一句话职责>, location: <project-root 相对 path>, status: 已核实|待核实}
```

**ID 铸号**：`AN-<nn>` **两位序号、从 01 起顺序递增、不重编不复用**；引擎核唯一性与顺序性（重号 `DUPLICATE_ID` / 跳号或乱序 `SET_MISMATCH` / 形态非法 `ENUM_INVALID`）。删掉一个组件时**不回收它的号**，并在 `revisions` 追加一条。

**取证纪律**：直接读源码得到的记 `status: 已核实`；由 README / 命名 / 目录推断的记 `status: 待核实`，并在 `revisions` 记 gap。**绝不把推断写成事实**。

### 1.2 分层（源 step-03 第 3 指令）

判定每条的 `layer`：**展示层**（UI 渲染与交互）/ **应用层**（用例与编排）/ **领域层**（业务规则与实体）/ **基础设施层**（数据库、外部 API、文件系统）。源侧提醒：**不是每个代码库都有干净分层**——照实记，**把跨层调用也记出来**（它是风险素材），不硬套四层；确实切不出来就记 `未分层`。

**落盘**：`components[]` + `architecture.layers[]`（把第 2 步的目录候选映射定稿为组件级归属）。

**检查点（六拍）**：① 生成 → ② 落盘 → ③ 分隔 → ④ 呈出 → ⑤ 出四选项 → ⑥ 等响应。本步：② 落盘（`components[]` 与 `layers[]`）；④ 呈出组件清单表。

## 第 2 步 —— 数据流端到端与外部集成（源 step-03 第 2、4 指令）

**先说清为什么**：讲清「为什么至少要走通一条完整链路」——只看组件等于只看地图不看路，链路上才藏着真实的耦合与延迟。用你自己的话讲。

### 2.1 端到端数据流（源 step-03 第 2 指令）

挑 **2–3 个**关键用户动作，逐条走完六段：**用户动作**（点击 / 提交 / 加载）→ **前端处理**（事件、状态、调用）→ **API 层**（路由、中间件、校验）→ **业务逻辑**（服务、领域、转换）→ **数据层**（查询、缓存、外部 API）→ **回程**（逐层回到 UI）。

落 `data_flow[]`，每条至少两键：`name`（这条流叫什么）+ `steps[]`（六段各一句）+ `components[]`（**引 `AN-<nn>`，不复制组件名**）。**至少一条完整走通**（源 `Document at least one complete flow end-to-end`）。

### 2.2 外部集成（源 step-03 第 4 指令）

列全代码库对外说话的每一个系统，逐条落 `dependencies[]`（键：`from` / `to` / `note`）：`from` 引 `AN-<nn>`，`to` 写外部系统名（数据库 / 支付 / 邮件 / 缓存 …），`note` 一句写协议与位置（例：`SQL via ORM，src/db/`）。

**落盘**：`data_flow[]` + `dependencies[]`。

**检查点（六拍）**：① 生成 → ② 落盘 → ③ 分隔 → ④ 呈出 → ⑤ 出四选项 → ⑥ 等响应。本步：② 落盘（`data_flow[]` / `dependencies[]`）；④ 呈出数据流与集成表。 四选项同第 1 步。

## 第 3 步 —— 状态、依赖图与架构模式（源 step-03 第 5–7 指令）

**先说清为什么**：讲清「为什么状态和依赖值得单列」——循环依赖与状态双源是两类最贵的隐性缺陷，它们不在任何单个文件里。用你自己的话讲。

### 3.1 状态管理（源 step-03 第 5 指令）

`architecture.overview` 增补一段：前端（全局 store / context / 局部 / URL 态）、后端（会话 / 数据库 / 缓存 / 内存）、以及**两端怎么同步**。

### 3.2 依赖图（源 step-03 第 6 指令）

把 `dependencies[]` 补成组件间关系：**高扇入**（被很多模块依赖的）与**高扇出**（依赖很多模块的）各点名；**循环依赖单列**；标注紧耦合与松耦合区。跨层调用（1.2 记下的）在此归位。

### 3.3 架构模式（源 step-03 第 7 指令）

`architecture.patterns[]` 定稿，按四类各写读到的（**没读到的不写**）：**结构**（MVC / MVVM / 整洁架构 / 六边形 / 单块 / 微服务）、**数据**（仓储 / Active Record / Data Mapper / CQRS）、**通信**（REST / GraphQL / WebSocket / 事件驱动 / 消息队列）、**错误处理**（集中式 / 逐模块 / try-catch / 错误边界）；测试策略（单元 / 集成 / e2e 的分工与打桩方式）另起一条。

**落盘**：`architecture.overview` 状态段 + `dependencies[]` 增补 + `architecture.patterns[]` 定稿。

**检查点（六拍）**：① 生成 → ② 落盘 → ③ 分隔 → ④ 呈出 → ⑤ 出四选项 → ⑥ 等响应。本步：② 落盘（三处）；④ 呈出状态 / 依赖 / 模式三项。 四选项同第 1 步。
