## 第 2 步 —— 技术栈与入口点（源 step-02 第 2–3 指令）

**先说清为什么**：讲清「为什么栈要从清单文件读、不从印象说」——版本号藏在清单里，印象里永远是「大概挺新的」。用你自己的话讲。

### 2.1 技术栈（源 step-02 第 2 指令）

读清单件，逐条落 `architecture.tech_stack[]`（**写成 `语言/框架 版本` 的短句**，一行一条）：

| 清单件 | 读出 |
| --- | --- |
| `package.json` / `requirements.txt` / `Cargo.toml` | 依赖、脚本、项目元数据 |
| `tsconfig.json` / `pyproject.toml` | 语言配置 |
| `.env.example` / `.env.template` | 需要哪些环境变量 |
| `docker-compose.yml` / `Dockerfile` | 容器与服务 |
| `Makefile` / `justfile` | 构建命令 |

**只记读到的**：清单件缺席就记 gap，绝不按项目类型猜栈。

### 2.2 入口点（源 step-02 第 3 指令）

按应用类型找执行起点：**Web 应用**（主页 / 路由 / 布局 / 应用入口）/ **API**（服务入口 / 路由定义 / 中间件链）/ **CLI**（主命令文件与参数解析）/ **库**（导出的模块与公开 API 面）。入口路径一律 project-root 相对 `path:line`。

**落盘**：`architecture.tech_stack[]` + `architecture.overview` 的入口一段。

**检查点（六拍）**：① 生成 → ② 落盘 → ③ 分隔 → ④ 呈出 → ⑤ 出四选项 → ⑥ 等响应。本步：② 落盘（`tech_stack[]` 与入口段）；④ 呈出栈与入口清单。 四选项同第 1 步。

## 第 3 步 —— 配置、构建管线与模式初判（源 step-02 第 4–6 指令）

**先说清为什么**：讲清「为什么环境配置也算架构」——同一份代码在 dev / prod 跑出两种行为，那是最贵的一类隐性耦合。用你自己的话讲。

### 3.1 配置面（源 step-02 第 4 指令）

扫会改变行为的配置：环境差异（dev / staging / prod）、特性开关、路由配置、数据库连接、第三方服务配置（认证 / 支付 / 邮件）。

### 3.2 构建与部署管线（源 step-02 第 5 指令）

找 CI/CD 配置（`.github/workflows/` / `.gitlab-ci.yml` / `Jenkinsfile`）、构建脚本与其产物、部署目标与流程、按环境区分的构建。

### 3.3 模式初判（源 step-02 第 6 指令）

扫的过程中顺手记初判（**一律记为 `待核实` 级的观察，下一步才定性**）：代码组织风格（单块 / 单仓多包 / 微服务）、命名约定（文件 / 目录 / 变量）、测试组织（同目录 / 独立目录 / 两者）、文档密度（齐 / 稀 / 过时）、质量信号（lint 配置 / 格式化配置 / 类型严格度）。

**落盘**：`architecture.patterns[]` 落初判条目（每条一句话），`architecture.layers[]` 落**目录层到架构层的候选映射**（`展示层|应用层|领域层|基础设施层|未分层`——下一步定稿）。

**检查点（六拍）**：① 生成 → ② 落盘 → ③ 分隔 → ④ 呈出 → ⑤ 出四选项 → ⑥ 等响应。本步：② 落盘（`patterns[]` / `layers[]`）；④ 呈出配置 / 管线 / 初判三项。 四选项同第 1 步。
