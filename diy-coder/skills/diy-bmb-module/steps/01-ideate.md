# Step 1 — 构思会话（Ideate）

Progress: `[构思会话] → 落计划 → 校验 → 终门与交付`

**Read (input):** 用户的议题（愿景 / 目标技能名 / 要补的能力）；`diy-coder.yaml` 的 `project.name`。
**Write (output):** `{output_dir}/module-plan.yaml` 的空骨架记录（只有身份字段）；对话里给出的探索过程。

## 定位与铸骨架

1. 确认议题：这批技能要解决什么、使用者是谁、为什么现在做。说不清 → 回激活段第 2 步的门禁，**零产出**。
2. 铸骨架：

```
python "{project-root}/.claude/skills/diy-bmb-module/scripts/bmb_module.py" new --slug "<计划的 slug>" --title "<计划标题>" --project-root "{project-root}" --output-dir "{output_dir}" --json
```

`ok: false` → 把违规码与消息转述给用户，零产出停止（重复 slug 会指认既有 `MP-xxx`——那是**更新**，不是新建）。

骨架里除 `id` / `slug` / `title` / `status` / `date` 外全是空值。**空值即「未写」**——这是把写作纪律写进文档本身：探索期只往对话里写，产物保持空，直到 step 2 才逐字段落。别为了「看起来完整」先填占位词。

## 创意探索

先把可能性摊开，再收敛。六件套按需取用，**别报菜名**：

- **第一性原理** — 剥掉假设：这件事核心解决什么问题？只能做一件事时做哪件？
- **What If** — 扩可能空间：还能是什么样？没有技术约束会怎样？
- **反向头脑风暴** — 从否定找约束：怎样会把这批技能做得最糟？再翻过来。
- **假设反转** — 挑战既有判断：真需要拆成多个技能吗？单个技能带多能力行不行？
- **视角切换** — 换位置问：使用者 / 后来维护的人 / 第一次遇到的人 / 怀疑者。
- **问题风暴** — 摊开未知：使用者第一次看到会问什么？我们还没想到的是什么？

只在对话里探索，**不往产物里写素材**。用户提前想结构化时，先收下再问一句「还有吗」。

## 架构建模（强制软门）

1. 收口前先问一次：「转架构之前还有要收的吗？」得到确认才继续。
2. **单技能 + 丰富能力优先于多技能**：多技能各自带上下文更重、注册面更大。只有满足下列之一才拆：服务不同使用旅程 / 需要不同工具面 / 阶段之间差异大到不同过程。
3. **每个技能必须产有形产物**——纯规划型、纯协调型技能是反模式（它的能力应摊进别的技能）。例外：用户明确要一个对话中枢。
4. 把取舍理由记进对话，step 2 落进 `skills[].brief` 的「设计取舍」行。

## 上下文与依赖

- **批次内依赖**：谁必须先造？写进 `build_order`（step 2）。依赖不是顺序偏好——是「不先有它，另一个造不下去」。
- **对既有能力的依赖**：要用 `diy-elicit`、`diy-spec` 这类已装技能吗？写进 `depends_on`（step 2）。**即使没有，也要显式想一遍**——空着和「想过且为空」是两回事。
- **外部依赖**：CLI 工具 / MCP 服务 / 需用户提供的凭据，逐个点名，不能只写「无」。

## 能力评审（不可跳过）

把这批技能的清单连同各自的 purpose 复述给用户，逐条问：

- 有漏的能力吗？有该合并的（太碎）？有该拆的（太粗）？
- 每个技能的边界说清了吗——它**不做**什么？
- 重复面：两个技能是不是在做同一件事？

改到用户确认为止。评审结论进 step 2 的 `skills[].brief` 与 `open_questions`。

## 播报与下一步

给用户一句话：这批几个技能、打算按什么顺序造、还有哪些未决问题。

读全并照做 `./02-plan.md`。
