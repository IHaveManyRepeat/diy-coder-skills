# 自改进闭环（opt-in）

当一次 run 失败或结果偏弱、用户又想据此改进技能时，按本闭环走。**先问用户**：自改进是 opt-in，不是默认续作。

## 零、按利害校准激进程度（先定，再开始）

- **一次性技能**（自己用、没别人依赖）：可以长循环、宽标准，跑得动就行。
- **被别人依赖的技能**（进主链、别的技能会调它）：短循环、严标准，且**每一处改动都由人逐条过目**。

先说出这是哪一档，再定轮数上限与通过条件；不校准就开跑，最后一定会在「不知道算不算改好」的地方停下。

## 一、每轮四拍

1. **Scan（扫）**——跑分析器：**用 `diy-bmb-builder` 的 Analyze 模式**对当前技能跑一遍质量分析，拿它的 findings 当本轮的问题清单（**不要去硬引用或复刻它的透镜清单**——分析面归它，本技能只消费结论）。
2. **Eval（评）**——用本技能自己的模式：`quality`（达 rubric 吗）/ `variant`（这一节值不值）/ `baseline`（还打得过裸模型吗）。**复评只认 run 目录里的数**。
3. **提议一个改动**——**一轮只提一个具体改动**。一次改五处，分数掉了也不知道是哪一处掉的。
4. **应用并复评**——应用后重跑同一套 case；**任何回落的轮次一律回退**（回退是纪律，不是失败）。

## 二、停止条件

达到通过条件，或触到轮数硬上限（上面校准的那一个），即停。停时把「改了什么 / 为什么 / 复评前后各多少」写进结论。

## 三、memlog 记四类条目

决策 `decision` / 方向 `direction` / 假设 `assumption` / 事件 `event`——随发生随追加（只追加、不重写历史）：

```
python "{project-root}/.claude/skills/diy-eval-runner/scripts/eval_runner.py" mlog --dir <run 目录> append --file .memlog.md --type decision --text "<一句话>" --project-root "{project-root}" --output-dir "{output_dir}"
```

## 四、泛化到意图，不要过拟合单个用例

改的方向要落在「这类输入该怎么处理」上，不是「这一条 case 怎么过」。黄旗：

- 出现一堆 `ALL-CAPS MUST` / 「务必/绝不」的规则堆。
- 新增的句子只在某一个 case 的输入下成立。
- 分数涨了，但同族的另一条 case 掉了——那是过拟合，不是改进。

看到黄旗就停下重想：是意图没写清，还是这条 case 本身该修。
