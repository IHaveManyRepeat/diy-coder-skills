# Step 2 — 单循环构建流

Progress: `意图路由与开场 → [构建单循环] → 五透镜分析 → 门禁与评测 → 交付收尾`

**Read (input):** 用户倒出的全部材料（目标、参考、既有技能、转录）；`mlog` 回执；`scaffold` / `template` 回执。
**Write (output):** 技能目录树（`{output-root}/<skill-name>/`）；`mlog` 条目；给用户的草稿展示。

## 这是一条循环，不是一个阶段序列

下面每一条是**「你想让它成真的一件事」**，不是要打卡的步骤。按对话准备好哪件就先做哪件，图景变清晰了就回头重做前面的。Build 与 Edit 共用同一条：Edit 就是同一条循环指向一个已经存在的技能——只读改动会碰到的那部分，其余不碰，不重新推导整份规格。

## 懂他为什么来

先弄清用户到底要拿到什么、以及在他眼里"好"长什么样，再动手读材料。开场那一倒已经做掉大半——读他倒的东西，从对话里挖工具、顺序、**他做过的每次纠正**、他已经给你看过的输入输出。只问还缺的。

## 扎进真专家知识

只凭模型的通识起草，发出去的就是通用流程；价值在只有这个项目知道的东西里。主动索要承载它的材料：runbook 与内部文档、事故报告与处理结论、代码评审意见、版本控制历史、或**一次手做同一件事的转录**——用户当时纠正的每一处，正是这个技能存在的意义（那些坑要编码进去）。技能从**一个**样例里提炼时，要教方法而不是那个样例的答案：做法要能泛化到下一个输入，哪怕细节仍然具体。

## 硬化想法，再动手

技能生成便宜、养起来贵。起草之前先压：**这是一个技能还是三个？它到底该不该是个技能**（一次性的事用户自己问一句就行）？唯一的产出是什么、谁消费？它跑在什么真输入上？哪里会薄、会在哪里失败？想法半成型就顶回去——**接受含糊想法的构建者，发出的是含糊技能**。

对着用户校准：他已经拿着硬邦邦的具体想法、或明说要快 → 确认形状就走，别磨；想法是生的 → 留在硬化对话里直到产出与范围清楚。

## 提议想法隐含的东西

硬化是把想法削小，这一步是把它补全。起草前，列出用户没要、但这个产出**必然想要**的东西：它满足条件的命名模式、明显的兄弟意图（create 旁边的 update / validate）、没人提但该接受的输入。一条一句附上"为什么合适"；用户勾选的进产物，**被否掉的落 memlog**，免得下次会话再提一遍。只执行被说出口的想法，发出的是用户的初稿。

## 全程写 memlog

决定和方向一落地就写，别攒到最后批量补——价值在趁推理还热的时候抓住它。

```
python "{project-root}/.claude/skills/diy-bmb-builder/scripts/bmb_builder.py" mlog --dir "{output_dir}/build-logs" append --file <skill-name>.md --type <decision|direction|assumption|gap|note|event> --text "<一句话>" --project-root "{project-root}" --output-dir "{output_dir}" --json
```

`decision` = 定了什么、`direction` = 往哪走、`assumption` = 无头态下替用户做的假设、`gap` = 已知缺口、`note` = 其它、`event` = 里程碑。全新技能用户没给名字时，你提议一个 hyphen-case 名（改了名是一条 `decision`，不是重做）。

## 先写最小版本

```
python "{project-root}/.claude/skills/diy-bmb-builder/scripts/bmb_builder.py" scaffold --name <skill-name> --dirs steps --project-root "{project-root}" --output-dir "{output_dir}" --json
```

落点默认 `{project-root}/.claude/skills/<skill-name>/`（**一步到位，落此即用**）；要把它变成套件的一部分（进 git 分发）才加 `--to-source` 落 `{project-root}/diy-coder/skills/<skill-name>/`（技能名须带 `diy-` 前缀）。`--dirs` 只 stub 这次真的需要的目录（`steps` 是默认，`references` / `scripts` / `assets` 按需加）。

起手 SKILL.md 已带四段骨架与母本冻结句，接着写**能跑通的最小版本**：写目的地，不写路线。其余一切结构**先都不加**，直到一次对比挣来它。Edit 意图要覆盖既有技能时：目标是**破坏性操作**——交互态先拿到用户明确确认才加 `--force`；**无头态不给 `--force`**，改跑 `diyc.py defer-add --reason 破坏性操作` 入队、明示、停。`--force` 有硬护栏：命中套件已建技能名或禁改面，即使 `--force` 也拒。

## 在真输入上跑

没跑过的技能是猜的。拿用户手上那份真实、脏的输入跑一遍最小版本。**读转录，不只读产物**——三种轨迹各自点名一种病：模型试了好几种解法才成 → 某句指令太含糊；模型照做了一条不适用的指令 → 指令太宽；模型在几个选项之间打转 → 没给默认。

## 只在两版对比要求时才加脚手架

不要凭感觉加结构。只有当**最小版在一个你能点名的具体点上失败**时才加。想加结构时先问一句：把产出那句话写得更利落，是不是就够了？多数时候就是够了——改那句话，跳过脚手架。

## 全程找脚本机会

这是构建者的看家本事，全程开着，不要当成一个检查点。判定三问：**同样输入是否永远同样输出？能不能写一个通过/失败的单元测试？是否需要理解语义与语气？** 前两问为是 → 是脚本活（提取、计数、校验、比对、格式转换）；第三问为是 → 留在提示词里。命中信号动词就找脚本：validate / count / extract / convert / compare / scan for / against schema / list all / detect / diff。**预扫 JSON 模式**：凡是要模型读原始文件才能拿到的少量事实（行数、token、frontmatter、文件清单），改由一个脚本读、吐紧凑 JSON，提示词只消费数字。非标准库依赖先列出并征得用户同意再依赖。

## 播报与下一步

给用户看这版技能（`SKILL.md` 与各步骤文件的要点）+ 你在 memlog 里记的关键决定。确认形状对了 → 读全并照做 `04-gate.md`。
