# Step 3 — 交叉验证（Cross Check）

Progress: `定位与切分 → 预演执行 → [交叉验证] → 落盘与交付`

**Read (input):** 草稿记录里的全部 findings 与单元清单。
**Write (output):** 新增 / 合并 / 删除后的 findings；重算后的 `summary`。

## 为什么要这一步

单次预演有两个系统性盲区：① 顺着读会**滑过**自己熟悉的领域（"这块我懂，没问题"）；② 报告容易**虚高**——把措辞偏好写成歧义。交叉验证同时对治这两个。

## 三个动作

### 1. 高风险单元换视角复扫

挑 2-4 个单元重扫，优先挑：① finding 最密集的；② 你预演时**最顺畅**的（顺畅往往意味着你在用背景知识填空）；③ 篇幅最大的。

复扫换落脚点——上次从第一行顺推，这次**从产出反推**："规格说最后要交出 X，那 X 的每个字段从哪来？谁写的？什么时候写？"反推能碰到顺推碰不到的断点。

### 2. 去误报（逐条过筛）

对每条已报 finding 问三个问题，任一为"是"就删或降级：

- **规格别处写了吗？** 它可能在后文或另一份文档里定义了。回去搜关键词，命中就删。
- **这是留给实现者的自由吗？** 有些决策就是有意留给实现者的（"自定"、"可选"、"按项目情况"）——那是设计意图，不是歧义。删。
- **这是我的措辞偏好吗？** 你在要求它换成你的写法——那是质量问题，不是执行歧义。删。

移除的条目在对话里列一句"移除 N 条 + 一句话理由"，不必写回 YAML。空缺号不回收、不重排（见 step 2 的号段规则）。

### 3. 补漏（对覆盖清单过筛）

看 `units` 清单：有没有"扫了但零 finding"的单元？零 finding 要么真的写得干净，要么是你滑过去了——挑其中 1-2 个用反推法快速过一遍。

## 收口

重算 `summary`（`total` / `blocker` / `major` / `minor` 与 findings 一致），确认所有 `units[].scanned` 为 `true`。

## 播报与下一步

给用户一句话：复扫了几个单元、补了几条、移除几条、余下 blocker 几条。

读全并照做 `./04-report.md`。
