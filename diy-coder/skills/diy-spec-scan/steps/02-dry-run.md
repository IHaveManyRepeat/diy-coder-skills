# Step 2 — 预演执行（Dry Run）

Progress: `Collect → [Dry Run] → Cross Check → Report`

**读入：** 当前单元对应的目标文件片段；已积累的 findings（避免重复报同一处）。
**写出：** 执行计划（对话里给出）；findings 追加进草稿记录；逐单元把 `scanned` 改 `true` 并重算 `summary`。

## 你要扮演谁

**实现者**——一个第一次拿到这份规格、要照着它干活的人。它聪明、守规矩，但对这份规格**没有任何背景知识**：规格没写的，它就是不知道。

预演的含义：拿一个单元，**从第一步往下走**，边走边问"我这一步具体做什么"。走不下去的地方，就是 finding。

## 硬纪律：执行计划先行

对每个单元，先在对话里写出执行计划——不是总结规格说了什么，是**你要做什么**：

```
单元 <名>（<path>:<起始行>）
1. 我做 X（输入：<从哪读>；输出：<写到哪>）
2. 我做 Y
3. 这里卡住：规格说"按优先级选范围"，但我不知道优先级从哪来
```

禁止出现的句式：`本单元描述了……` / `这份规格要求……` / `整体来看……`（那是读后感，不是预演）。
必须出现的句式：`我第 N 步做……` / `我从 <路径> 读……` / `我把结果写到……` / `这里我必须猜……`。

## 八类判据（走到哪问到哪）

每个决策点依次问这八个问题；命中任何一个，记一条 finding。

| 类型 | 问自己 | 命中长相 |
|------|--------|---------|
| `INPUT_UNDEFINED` | 「我动手前该读什么？从哪读？读哪些字段？」 | 要读的东西没点名，或字段名在别处才对得上 |
| `OUTPUT_UNDEFINED` | 「我的产出写哪？什么格式？谁读它？」 | 产物路径 / 格式 / 消费者没写全 |
| `UNDEFINED_BRANCH` | 「如果遇到 X，我做什么？」 | 提到了某条件 / 异常 / 边界，但没给处置 |
| `ORDER_AMBIGUOUS` | 「这两步谁先谁后？换过来结果一样吗？」 | 顺序未定且顺序影响结果 |
| `TERM_CONFLICT` | 「这里说的是不是就是那边那件事？」 | 同一动作两处两个说法，或同一词两处两个含义 |
| `CONFLICT` | 「这两条能同时成立吗？」 | 两处内容直接对立（不是措辞差异） |
| `INTERFACE_GAP` | 「我的产出交给谁？那边接得住吗？」 | 下游 / 上游没有对应的接收或供给条款 |
| `UNSTATED_ASSUMPTION` | 「我凭什么知道这件事？规格里说了吗？」 | 你没卡住，但答得上来是靠规格外的知识 |

`UNSTATED_ASSUMPTION` 最容易被漏掉——因为你**没感觉到卡**。检测方法：每答完一个决策，追问一句"这个答案规格里写了吗"；如果答案是"这是常识 / 惯例 / 前面提到过"，回去核对；核对不到就是它。

## 一条 finding 要写全字段

```yaml
      - id: SS-001-01                  # 扫描序号 + 两位流水号，连续不跳号
        type: <八类之一>
        where: <相对路径>:<行号>        # 原文所在位置；跨多处时写最主要那处
        quote: <原文摘录>               # 逐字，机器锚点不翻译；长句截关键片段
        read_as: <我读到什么>           # 一句话：这句话在当前语境下的含义
        stuck: <我卡在哪>               # 一句话：要做什么决策，为什么定不了
        would_guess: <我会猜成什么>     # 命根子：没人管的话我照哪种理解干
        impact: <猜错的后果>            # 一句话：猜偏了会怎样
        suggestion: <建议怎么裁定>      # 一句话：补什么能消歧（可选但强烈建议）
        severity: blocker|major|minor
```

**severity 判据**：

- `blocker` — 两种理解会导致**完全不同的实现**，做错要推倒重来
- `major` — 导致局部偏差，需要返工一轮
- `minor` — 措辞瑕疵，实现者大概率猜对，但不该留

拿不准就往 `major` 放，别升 `blocker`；blocker 泛滥会让清单失去优先级。

## 逐单元推进

- **一批一批来**：单元多的时候（20+），每批 3-5 个，写完这批的执行计划与 findings 再开下一批。不要试图一次读完整个目标。
- **每批收尾**：把该批单元 `scanned` 改 `true`、重算 `summary` 计数、findings 追加写回 `{output_dir}/spec-scan.yaml`。这是状态写回（断点恢复靠它），不是产物改写。
- **同一处只报一次**：后续单元遇到与已报条目同源的问题，合并进原 finding（`stuck` 里补一句"另见 <位置>"），不新建条目。

## 跨单元 / 跨文件的问题

有些歧义只在两个单元对照时才出现（A 单元说要 X，B 单元说要非 X）。这类 finding 的 `where` 写主要那个位置，`read_as` 里点名另一处位置。

规格点名要参考的其他文档（任务书、契约、对接口技能的 `SKILL.md` / `steps/`）——读它们来判定接口类歧义（`INTERFACE_GAP` / `TERM_CONFLICT`），但**不读实现代码和产物实例**（见 SKILL.md Rules）。
