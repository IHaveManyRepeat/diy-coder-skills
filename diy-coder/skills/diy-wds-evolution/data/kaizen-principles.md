## 一、Kaizen 与 Kaikaku（两种改善）

**Kaizen（改善）= 持续改进**。循环永不停止：

```
Ship → Monitor → Learn → Improve → Ship → Monitor → Learn…
```

| | Kaizen（改善） | Kaikaku（改革） |
| --- | --- | --- |
| 体量 | 小、增量 | 大、激进 |
| 周期 | 1–2 周一轮 | 数月 |
| 成本 / 风险 | 低 / 低 | 高 / 高 |
| 发生次数 | 持续、不停 | 一次性转型 |
| 对应 | **本技能（棕地演进）** | 新产品开发（Greenfield） |

**入口术语（源 `data/existing-product-guide.md` 的两入口，该文件唯一不可替代段）**：

- **Greenfield**（从零建、无既有约束）对 **Brownfield**（在既有系统与约束里做）
- 本技能只接 **Brownfield**；从零建走 `diy-wds-brief`（官网线）或 `diy-prd`（产品线）
- **Brownfield 也仍要一份「简版简报」**——不是跳过立项，而是把立项收窄成四问：这次解决什么战略挑战 / 范围是什么 / 成功判据是什么 / 约束是什么（落 `rounds[].analysis` 的 `current_state` 与 `selected_rationale`）

## 二、四条原则

### 原则 1：盯过程，不只盯结果

- **坏**：「我们要把使用率提上去！」（只有压力，没有学习）
- **好**：「先搞清使用率为什么低，立一个假设，测它，量一下影响，学到点什么。」

Kaizen 的产出**一半是数字、一半是认知**。只盯结果时，失败什么也学不到。

### 原则 2：消除 Muda（無駄，浪费）

设计工作里的七类浪费（源逐条）：

| 浪费 | 在设计里长什么样 |
| --- | --- |
| 过度生产 | 做没人用的功能 |
| 等待 | 卡在审批或开发上 |
| 搬运 | 交接摩擦 |
| 过度加工 | 在低影响的功能上反复打磨 |
| 库存 | 做完却没发出去的稿 |
| 动作 | 低效的流程本身 |
| 缺陷 | Bug 与返工 |

**Kaizen 消它的四条路**：小范围改进 · 短循环（ship → learn → improve）· 持续测量 · 从每一轮里学。

### 原则 3：尊重人与人的洞见

要听的人：用户（反馈与行为）· 开发（技术实情）· 支持（痛点）· 干系人（业务语境）· 团队（观察）。**每一类人都可能握着你缺的那半个事实。**

### 原则 4：先标准化，再改进

找到一条**好用的模式**之后：

1. **记下来**（什么时候用 / 怎么实施 / 预期影响——三段）
2. **做成可复用的件**（下次不用重想）
3. **分享**（团队用同一套）
4. **再改进它**（从每次应用里修）

**没有第 1 步，第 4 步无从发生**——不写下来的模式，改进只会发生在想得起来的人身上。

## 四、小改动会复利

源侧给出的轨迹（四个月九轮，逐月）：

```
第 1 月：功能 X 引导（使用率 +40%）
第 2 月：功能 Y 引导（+60%）· 功能 Z 性能（留存 +15%）
第 3 月：功能 X 精修（+7%）· 引导组件库（可复用）· 功能 W 引导（+50%）
第 4 月：看板性能（参与度 +20%）· 导航改进（可发现性 +10%）· 错误处理（恢复率 +30%）
```

**每一轮 1–2 周；小改动复利。**

## 五、何时暂停

**Kaizen 永不停，但可以暂停**——三种情形：

| 情形 | 长什么样 |
| --- | --- |
| 重大战略转向 | 新产品方向 / 转向或改品牌 / 需要整体重设计（那已是 Kaikaku，不属本技能） |
| 团队容量 | 团队被压垮 / 要补历史欠账 / 需要先稳住 |
| 测量期 | 等数据 / 季节性波动 / 外部因素 |

**但总要回到 Kaizen**——暂停是**等一个数**，不是结束。三种情形之外，没有「这轮做完先歇歇」这一档。

## 六、一轮的判定（本技能把它落成机械判据）

| Kaizen 说法 | 本技能的产物键与判据 |
| --- | --- |
| 一次一条 | `rounds[EV-<nn>].target` 恰一条；未选中的进 `kaizen_priority.candidates[]` |
| 小范围 | `scope.pages_affected[]` 逐页点名、`scope.risk` 三档（`High` 必须明说超出常规体量并给拆分选项） |
| 先立根因 | `analysis.root_cause` / `.hypothesis` / `.validation_plan` 三键非空 |
| 可量 | `scope.success_criteria` 带数字与时点；`design.acceptance_criteria[]` 逐条可测 |
| 学到点什么 | `design.hypothesis.failure_criteria[]`——**只写成功判据的假设，验不了伪** |
| 盯过程 | `test.criteria[]` 逐条给 `actual`（不写「符合预期」这类结论词）；`delivery.monitoring.watch_for[]` |
| 迭代不停 | `delivery.next` 必填（下一目标或「待新一轮分析」） |
