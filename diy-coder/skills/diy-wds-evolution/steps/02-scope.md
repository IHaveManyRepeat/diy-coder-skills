## 第 2 步 —— 定义变更（源 [S] step-02）

**先说清为什么**：为什么「现状 / 期望态 / 成功判据」三件事要分开写——写在一起时，人会不自觉地把现状描述成已经接近期望态，成功判据就再也立不住了。用你自己的话讲。

**四问（源 [S] step-02 的 1–4，逐条问、不许并成一问）**：

1. **改哪一页 / 哪一段流？**（**具体到一个页或一条流的一段**——答「整个站点」就打回）
2. **现状**——用户今天看到什么？哪里不对？（带证据：数字或原话）
3. **期望态**——改完之后用户经历什么？（一句话，不要写成方案）
4. **成功判据**——怎么知道它成了？（**可量则带数字与时点**）

**产出键**：`scope.page` / `scope.current_state` / `scope.desired_state` / `scope.success_criteria`。

**落盘**：本步不写盘（第 5 步一次性成稿，避免半份场景被下游误引）。

**检查点（六拍）**：① 生成 → ② 落盘（本步无写盘）→ ③ 分隔 → ④ 呈出四问的答案 → ⑤ 出四选项 → ⑥ 等响应。四选项同第 1 步。

## 第 3 步 —— 微旅程映射（源 [S] step-03）

**先说清为什么**：为什么要在这**一页**里再走一遍用户的路——痛点常常不在「页面本身」，而在用户**怎么进来、出去之后去哪**。用你自己的话讲。

**四问（源 [S] step-03 的 1–4）**：

1. **入口**——用户怎么走到这一页？（从哪来、带着什么期待）
2. **现状流**——今天一步一步发生什么？
3. **痛点**——**具体在哪一步**断掉？（点名到步）
4. **建议流**——改完之后一步一步发生什么？

**产出键**：`scope.journey: {entry, current_flow, pain_points, proposed_flow}`。三步以内就写完——**超过五步说明这次的范围大了**，回第 2 步收窄。

**落盘**：本步不写盘。

**检查点（六拍）**：① 生成 → ② 落盘（本步无写盘）→ ③ 分隔 → ④ 呈出两条流（现状 / 建议）并排 → ⑤ 出四选项 → ⑥ 等响应。四选项同第 1 步。

## 第 4 步 —— 范围估算（源 [S] step-04）

**先说清为什么**：为什么小改动也要估一次——估算的用处不是排期，是**发现这次其实不小**。用你自己的话讲。

**四栏（源 [S] step-04 逐字）**：

- **受影响页**：逐页点名（**不是**「相关页面」）
- **被触组件**：哪些 UI 件会变（新增 / 修改 / 删除三分）
- **数据变更**：有没有 API 或数据模型要动
- **风险三档**：`Low`（纯视觉）/ `Medium`（行为改变）/ `High`（结构性改变）

**`High` 的处理**（源侧把 Kaizen 的规模判据压在「1–2 周」）：`High` **不禁止**，但必须在本步**明说「这已经超出一次 Kaizen 的常规体量」**并把拆分选项摆给用户——拆，还是就承认这是一次 Kaikaku（源 `data/existing-product-guide.md` 的术语：改革式的大改属 Phases 1–7，不属本技能）。

**产出键**：`scope.pages_affected[]` / `scope.components_touched` / `scope.data_changes` / `scope.risk`。

**落盘**：本步不写盘。

**检查点（六拍）**：① 生成 → ② 落盘（本步无写盘）→ ③ 分隔 → ④ 呈出四栏 + 风险档 → ⑤ 出四选项 → ⑥ 等响应。四选项同第 1 步。
