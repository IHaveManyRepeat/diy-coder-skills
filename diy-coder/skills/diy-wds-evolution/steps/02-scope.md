Progress: `[1 载分析 → 2 定义变更 → 3 微旅程映射 → 4 范围估算 → 5 场景落盘与呈批（用户关卡 2）] → ./03-design.md`

**Read (input):** 本产物 `rounds[EV-<nn>].analysis` 的 `root_cause` / `hypothesis` / `selection`（上一文件已落盘）；`{output_dir}/analysis.yaml`（**按需，非必读**——第 4 步估范围已声明依赖时才读）；`data/kaizen-principles.md` 的「小批量」纪律；用户对「改哪一页、改到什么程度」的回答。

你是**范围的守门人**。这一步的全部价值是**把「想要」压成「这一次只做这一件」**——Kaizen 的规模判据是「一次一条工作流里的一段」，超了就退回。

**本段纪律（源 [S] 与 `steps-d/step-01` 的共同要求）**：① 一次变更 = **一页 / 一条流的一段**，不许「顺手也改一下」；② 成功判据必须**可量**（带数字与时点）；③ 边界要写**不做什么**——比写「做什么」更能挡住蔓延。

## 第 2 步 —— 定义变更（源 [S] step-02）

**先说清为什么**：为什么「现状 / 期望态 / 成功判据」三件事要分开写——写在一起时，人会不自觉地把现状描述成已经接近期望态，成功判据就再也立不住了。用你自己的话讲。

**四问（源 [S] step-02 的 1–4，逐条问、不许并成一问）**：

1. **改哪一页 / 哪一段流？**（**具体到一个页或一条流的一段**——答「整个站点」就打回）
2. **现状**——用户今天看到什么？哪里不对？（带证据：数字或原话）
3. **期望态**——改完之后用户经历什么？（一句话，不要写成方案）
4. **成功判据**——怎么知道它成了？（**可量则带数字与时点**）

**产出键**：`scope.page` / `scope.current_state` / `scope.desired_state` / `scope.success_criteria`。

**落盘**：本步不写盘（第 5 步一次性成稿，避免半份场景被下游误引）。

**检查点（六拍）**：① 生成 → ② 落盘（本步无写盘）→ ③ 分隔 → ④ 呈出四问的答案 → ⑤ 出四选项 → ⑥ 等响应。四选项同第 1 步。

## 第 3 步 —— 微旅程映射（源 [S] step-03）

**先说清为什么**：为什么要在这**一页**里再走一遍用户的路——痛点常常不在「页面本身」，而在用户**怎么进来、出去之后去哪**。用你自己的话讲。

**四问（源 [S] step-03 的 1–4）**：

1. **入口**——用户怎么走到这一页？（从哪来、带着什么期待）
2. **现状流**——今天一步一步发生什么？
3. **痛点**——**具体在哪一步**断掉？（点名到步）
4. **建议流**——改完之后一步一步发生什么？

**产出键**：`scope.journey: {entry, current_flow, pain_points, proposed_flow}`。三步以内就写完——**超过五步说明这次的范围大了**，回第 2 步收窄。

**落盘**：本步不写盘。

**检查点（六拍）**：① 生成 → ② 落盘（本步无写盘）→ ③ 分隔 → ④ 呈出两条流（现状 / 建议）并排 → ⑤ 出四选项 → ⑥ 等响应。四选项同第 1 步。

## 第 4 步 —— 范围估算（源 [S] step-04）

**先说清为什么**：为什么小改动也要估一次——估算的用处不是排期，是**发现这次其实不小**。用你自己的话讲。

**四栏（源 [S] step-04 逐字）**：

- **受影响页**：逐页点名（**不是**「相关页面」）
- **被触组件**：哪些 UI 件会变（新增 / 修改 / 删除三分）
- **数据变更**：有没有 API 或数据模型要动
- **风险三档**：`Low`（纯视觉）/ `Medium`（行为改变）/ `High`（结构性改变）

**`High` 的处理**（Kaizen 的规模判据是「1–2 周」）：`High` **不禁止**，但必须在本步**明说「这已经超出一次 Kaizen 的常规体量」**并把拆分选项摆给用户——拆，还是就承认这是一次 Kaikaku（改革式的大改不属本技能）。

**接线句（S 相·引用＋推定分离，已裁口径）**：已声明依赖（轮级 `analysis_refs`，与 A 相共享）时读 `{output_dir}/analysis.yaml`——
- `components_touched` 按 `analysis.yaml.components[]` 的 `AN-<nn>` 锚**引用**：`new` / `modified` / `removed` 三分**由当次勘察判定**，不搬产物字段（产物无此三字段）；
- `data_changes` 由 `data_flow` / `dependencies` ＋当次勘察**推定**，不搬产物字段；
- `scope.risk` ＝**本次变更**风险（`Low`|`Medium`|`High`），**不直接搬** `risks[].severity`（高 / 中 / 低）——语义差已裁：scope 三字段是「变更×代码库」的关系属性、随轮落 `rounds[].scope`；`analysis.yaml` 是多轮共用的实体记录。
- **依赖已声明而 `analysis.yaml` 缺席 / 损坏 / 锚悬空 → 停手显式报错（一档）**——`check` 机械核 `MISSING_FILE` / `UNPARSABLE_YAML` / `UNKNOWN_ID`；不依赖的轮次不写声明、不受阻。

**步骤纪律（引用 `analysis.yaml` 五条，01-analyze 同款）**：① 只有本轮范围与 `analysis.yaml.question` 相关才可引其 AN 锚——**引擎不判语义**，会话须显式核对；② 只引 `project.status: 已定稿` 的 analysis；若引草稿，须在 `analysis.sources[]` / `open_questions` 明示「证据未定稿」；③ `analysis.yaml` 是**单问产物**——不同问题新跑 `diy-analyze`，不得拿旧分析充数；④ 不依赖轮次不写 `analysis_refs`、不读 `analysis.yaml`；⑤ `AN-<nn>` 唯一 / 顺序有效性归 `diy-analyze` 终门，本技能只核引用锚在场，不重复实现该校验。

**产出键**：`scope.pages_affected[]` / `scope.components_touched` / `scope.data_changes` / `scope.risk`。

**落盘**：本步不写盘。

**检查点（六拍）**：① 生成 → ② 落盘（本步无写盘）→ ③ 分隔 → ④ 呈出四栏 + 风险档 → ⑤ 出四选项 → ⑥ 等响应。四选项同第 1 步。

## 第 5 步 —— 场景落盘与呈批（用户关卡 2，源 [S] step-05）

**先说清为什么**：为什么这份场景要用户点头才算数——它是 [D]/[I]/[T] 三步共同的**唯一靶子**；靶子没定，后面三次「对不上」都要重来。用你自己的话讲。

**场景文档 6 段（源 [S] step-05 的模板，逐段对应到产物键）**：

```yaml
scope:
  target: <第 2 步的四问合成——改什么、为什么>
  page: <改哪一页 / 哪一段流>
  current_state: <用户今天经历什么>
  desired_state: <改完之后经历什么>
  journey: {entry, current_flow, pain_points, proposed_flow}   # 第 3 步
  success_criteria: <怎么量>
  pages_affected: []                                           # 第 4 步
  components_touched: {new: [], modified: [], removed: []}
  data_changes: <无 | 具体变更>
  risk: Low|Medium|High
```

**呈批（用户关卡 2）**：把上面六段整块呈出，`**没拿到明确点头不许往下走**`。点头后才落盘。

**产出键**：`rounds[EV-<nn>].scope` 整段（源 6 段逐段对应到键）。

**落盘**：`rounds[EV-<nn>].scope` 整段 + `rounds[EV-<nn>].status: 范围` + `project.updated`。

**检查点（六拍）**：① 生成 → ② 落盘（`scope` 段 + 状态推进）→ ③ 分隔 → ④ 呈出六段 → ⑤ 出四选项 → ⑥ 等响应。四选项同第 1 步。

**收尾与路由**：场景已定、范围已锁，读 `./03-design.md` 出方案。
