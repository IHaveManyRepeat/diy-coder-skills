## 第 2 步 —— 建分支（源 [I] step-02）

**先说清为什么**：为什么每条改进单独一个分支——[T] 阶段要拿 `diff` 当**测试边界**；改动混在主干上，「这轮到底动了什么」就没有机械答案了。用你自己的话讲。

**一条命令（源 [I] step-02 逐字）**：

```
git checkout -b evolution/<场景名 slug>
```

- 命名 = `evolution/` 前缀 + 场景名的 kebab-case slug（**由 `scope.page` 或本轮 `id` 派生**，如 `evolution/feature-x-onboarding`）。
- **分支已存在** → 不要 `-B` 强建（会丢已有提交）；先问用户是**切过去接着做**还是**换名**。
- **项目不是 git 仓库** → **不做任何 git 动作**，在 `implement.branch` 里写 `none` 并在会话里一行说明「本轮无分支隔离，改动直接落在工作区」——**不许替用户 `git init`**（那是改用户环境）。

**产出键**：`implement.branch`。

**落盘**：`rounds[EV-<nn>].implement.branch`（先落这一格，后面第 4 步再补全）。

## 第 5 步 —— 自检（源 [I] step-05）

**先说清为什么**：为什么自检要在交给 [T] 之前跑一遍——[T] 判的是「规格满足没有」，自检判的是「有没有把别的东西弄坏」；两件事的靶子不同，漏一件都要返工。用你自己的话讲。

**四查（源 [I] step-05 的 1–4）**：

1. **Diff 全部改动**：`git diff evolution/<场景名>..main`（非 git 项目 → 用第 4 步的 `implement.files[]` 逐文件核对）
2. **对规格**：`design.acceptance_criteria[]` **逐条**问「现在满足了吗」（不满足的当场补，别推给 [T]）
3. **无意外副作用**：清单外的页 / 件是否仍工作？（源侧原文 `other pages/components still work?`）
4. **清干净**：无调试代码、无注释掉的整块、无无关改动

**产出键**：`implement.self_review: {diff_checked, criteria_addressed: [], side_effects: [], cleanup: <做了/未做>}`。

**落盘**：`implement.self_review` + `project.updated`。

**检查点（六拍）**：① 生成 → ② 落盘（`implement.self_review`）→ ③ 分隔 → ④ 呈出四查结果 → ⑤ 出四选项 → ⑥ 等响应。四选项同第 1 步。
