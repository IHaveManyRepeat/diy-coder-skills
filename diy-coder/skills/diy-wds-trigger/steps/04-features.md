## 第 1 步 —— 特征影响（源 step-06a–06e）

**先说清为什么**：讲清「为什么有了人物和驱动因素还要给功能排序」——设计注意力有限，**先做哪个功能**要用「它对谁、影响多大」来答，不能凭手感。用你自己的话讲。

### 1.1 提取特征（源 06a）

**静默读** `wds-brief.yaml` 的产品概念与（在场的）`prd.yaml` 的 `features[]`，抽出**战略相关**的特征：

- **取**：核心产品特征、用户交互与流程、内容 / 沟通要素、关键差异点、（提到且战略相关的）基础设施。
- **跳过**：基础认证（登录 / 登出）、标准用户资料、基础 CRUD——**除非它本身独特或战略相关**。

**呈编号清单待改**：允许用户**增、改、并、拆**（源侧硬要求：`Not allowing user to edit the list` = SYSTEM FAILURE）。清单确认后才进 1.3。

**产出键**：`feature_impact[]` 的骨架（每条先落 `id` + `name`）。

### 1.2 校准评分办法（源 06b）

**先讲清怎么打**（源 `step-06b:59-79` 的原文口径）：

| 打分对象 | 高 | 中 | 低 |
| --- | ---: | ---: | ---: |
| **主人物**（`priority: 主`） | 5 | 3 | 1 |
| **其他人物** | 3 | 1 | 0 |

`max = 5 + 3×(人物数−1)`；**Must-Have 判据** = 主人物命中「高」**或** 总分 ≥ `max − 3`。讲完问一句「**清楚了就开打？**」——**用户点头才进 1.3**。

### 1.3 逐特征评分（源 06c）

对每条特征、对每个人物打 高 / 中 / 低，判据取**已写下的驱动因素**（不是印象）：

- **高**：直接命中一条主要 WANT（正向驱动）或直接挡住一条主要 FEAR（负向驱动）；是人物转型或成功的核心。
- **中**：有帮助但不关键；间接支持 wants / fears；锦上添花。
- **低**：跟这群人基本无关；不触及他们的驱动因素；背景 / 基础设施类。

**落盘**：每条 `scores: {primary: 高|中|低, others: [高|中|低, …]}`（`others` 条数 = 人物数 − 1，顺序与 `personas[]` 中**除主人物外**的记录同序）+ 重算出的 `score`。**评分必须能重算对上**（`check --final` 逐条重算，不符报 `SET_MISMATCH`）。

**呈排名表待调**（源 `step-06c:88-106`）：按总分排、标出主人物影响与 Top 特征；问「**这些评分你认吗？哪条要改？**」——改了就**重算、重排、再确认**，循环到点头。

### 1.4 成表与三档结论（源 06d–06e）

- `decision`（源侧 Must Have / Consider / Defer 的 diy 口径，取套件既有 MoSCoW 词表）：**必须**（Must Have）/ **应该**（Consider for MVP）/ **可选**（Defer）。
- 机械一致性（`check --final` 核对）：判「必须」须满足 1.2 的 Must-Have 判据；**主人物命中「高」的特征不得判「可选」**（源 `steps-v/step-04:72-74` 硬规则）。
- `rationale`：每条一句，**点名它命中哪条驱动因素 ID**（`DF-<n>.<m>±`）——这是「界面为什么这样设计」的追溯锚。
- 源侧的 `06-Feature-Impact.md` / `feature-impact-analysis.md`（**同一产物两个名字**，源侧缺陷）在 diy **不落盘 md**：成品就是 `feature_impact[]`；`templates/feature-impact.template.md` 的「评分图例 / 排名表 / 三档结论」三块**收编进本节**，不另建模板文件。

**用户关卡**：三档结论念一遍（必须 / 应该 / 可选各几条、分别是哪些），问「**这样分档你认吗？**」——**没点头不落盘**。
