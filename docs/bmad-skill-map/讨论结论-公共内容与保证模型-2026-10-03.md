# 公共内容维护与保证模型——讨论结论（2026-10-03）

> 跨会话续接文档：清理上下文后从这里恢复。待办正式登记在 `diy技能名录与审查底单.md` 末尾，本文是通俗版讨论结论。

## 起因

想给所有技能加一条「回复纪律：精简、名词准确」，发现公共内容每加一条要手工改 50 个技能文件。由此翻出旧机制、证伪旧理由、敲定新方案方向。

## 旧机制：母本复制

- 母本 = `diy-coder/.analysis/2026-09-16-skill-remediation/suite-texts.md`，全库重复的整句/整块都收敛在这里，技能逐字复制。
- 守卫 = `test_suite_texts.py`，断言片段在各成员文件里逐字一致（抓漂移）。
- 痛点：改母本一处，落地要手工改 N 个文件。

## 旧理由与证伪（2026-10-03 用户三连问）

当年不用「一处改处处生效」的三条理由：

1. **NFR-4「单技能拷走就能用」——已证伪**。47 个技能都调 `diy-tools/scripts/diyc.py`，少拷 diy-tools 当场全断；分发单元事实上是**整套 skills 目录**，单技能自包含从未成立。公共文件放共享处与 diy-tools 依赖同级，无新增风险。
2. 「SKILL.md 无 include」——仍成立，但只排除语法级包含，不排除读文件模式（steps/ 本来就是运行时读的）。
3. 「激活即全文进上下文」（在场性）——仍成立但**降权**：在场只是降摩擦，不是保证（见下）。

## 保证模型（本轮最重要的结论）

**保证只来自「必经引擎关卡」；提示词层只降摩擦、不供保证。**

- 引擎关卡 = 必经 + 自行计算 + 显式拒绝不代建。例：产物骨架必须 `init` 铸、终门 `exit 0` 唯一放行、output_dir 不存在 → `MISSING_FILE` 拒绝且不代建目录（diyc_lib.py:369-376）。
- 提示词（母本句、缺省链、内联/外置、在场性）= 让顺路的人顺路。模型跳过某句提示词拦不住，但后续关卡让它**走不通**、被迫回头。
- 无关卡可设的（如回复语言 zh-CN）永远在概率区，只能靠指令在场 + 人工抽查。

一句话：评估任何公共条款，**先问有没有关卡，再谈怎么写**。

## 新方案：两案待拍板（A vs B''）

条款处置序已定：**能下沉引擎关卡者优先下沉；无关卡的才留指令层。**

**方案 A：母本注入脚本（内联，倾向推荐）**
- `diy-coder/sync_texts.py`：母本片段用标记对 `<!-- suite:§N -->` 包围，脚本按成员清单自动替换全库标记对内内容。
- 流程 = 改母本一处 → 跑脚本 → 全库齐；`test_suite_texts.py` 照旧终态校验；母本升格为活文件 `diy-coder/suite-texts.md`。
- 优：纪律激活即在场、零额外 Read。劣：多一个脚本机制；改条款要跑脚本+重分发。

**方案 B''：共享文件 + 一行引用**
- 公共纪律放一处（如 diy-tools 下），各 SKILL.md 写一行「先读 X 并全程遵守」。
- 优：改一处即生效、零同步机制。劣：每次激活多一次 Read；纪律在场依赖模型执行读取指令（steps/ 模式证明遵循度高，但约束权重无证据）。

**待拍板**：A（在场性优先）vs B''（维护极简）——偏好问题，非技术事实。首次落地两案都要动 50 个文件。

## 配套下沉项（已定）

`diyc.py resolve` 回执扩 `communication_language` / `document_output_language` 两键（现公共键仅 project_root/output_dir/instance/violations/warnings/counts，diyc_lib.py:198）。母本 §3「读 yaml 模型自解析」改写为「跑回执取值」，与 §1 实例解析同构。语言**遵守**无法机械验证，但取值来源可机械化。
