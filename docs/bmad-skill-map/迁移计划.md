## 二、迁移定义（验收标准）

「迁移」= 把 BMAD 技能改造成 diy 形态，**不是复制文件**。每个技能迁完必须满足：

| # | 验收项 | 说明 |
| --- | --- | --- |
| 1 | `diy-coder/skills/diy-<name>/SKILL.md` | 薄主文件（On Activation / Workflow 概览 / Schema / Rules 四段，面向 AI 的指令式）+ 厚子文件按需加载（`steps/`、`modes/` 子目录；镜像 WDS step-file 架构：主文件给路由，细节绝不进主文件）。install.py copytree 已支持子目录递归同步 |
| 2 | 产物 YAML schema | 落 `diy-output/`，单一源；有稳定 ID 前缀 |
| 3 | 前置门禁 | 明确依赖哪个上游产物，不满足时拒绝并给出路由（零产出退出） |
| 4 | ID 链接入 | 引用上游 FR/AC/TC/D ID；产出 ID 可被下游引用；悬空由 viewer 标红 |
| 5 | 注册 | `bash diy-coder/sync.sh` 后 `.claude/skills/diy-<name>/` 存在 |
| 6 | viewer 渲染 | 新产物类型能被 viewer 渲染，或明确走通用降级并记录 |
| 7 | 冒烟 TC | 至少 1 条测试用例覆盖（走查 SKILL.md 契约 / 门禁拒绝路径） |
| 8 | 登记元数据 | `phase` / `precededBy` / `followedBy` / `required` / 产物路径，**直接取自 `raw/skill-map.json`** |
| 9 | 读取成本纪律 | On Activation 明确读哪几个文件；默认跳过 `detail` 段；大集合产物按 ID 定位读取；校验/统计类读取走脚本，模型只读结论简报 |
| 10 | 双源输入声明（交汇技能） | diy-design / diy-architecture / diy-dev 等处于双线交汇点的技能，须在 On Activation 判定输入源（主线产物 prd.yaml/sprint.yaml 或 WDS 线产物 wds-*.yaml），并分别声明门禁条件与回填目标；单一技能内分支，不复制技能 |
| 11 | 渲染静默（GUI 纪律） | 技能内对 viewer 的调用保持静默旁路：只写调用命令，不得新增「打开浏览器 / 报告路径等待查看 / 阻塞等待」类交互点；打开行为由 viewer 判定——AI/自动化环境不开，仅人工交互终端（TTY）自动开，非交互需显式 `--open`（2026-09-13 裁定，见第七节已定） |
| 12 | diyc 脚本接线（2026-09-13 增补） | 新技能一律：（a）On Activation 委托 `diyc.py resolve` 解析实例（禁手写实例解析/白名单——套件曾 5 处各自实现）；(b) 终门句 `diyc.py check --type <T> --final`，exit 0 唯一放行、回执为证据；(c) Update 前 ID 稳定走 `--previous`；(d) 语言绑定沿用套件统一模板（`communication_language` / `document_output_language` / `paths.output_dir` 三分工，机器锚点逐字保留）；(e) Rules 段声明写权边界（本技能只写哪些文件/字段）。模板：终门/计数句见 batch3-contract §8；实例样板句与写作纪律块以 `batch4/frozen-texts.md` 冻结版逐字复制（2026-09-13） |
| 13 | 副作用纪律（2026-09-15 修订） | 技能**运行时**的外部动作三档处置：① 写代码/测试链条内（依赖安装含浏览器与运行时下载 / 跑项目测试 / 构建 lint / 技能自生成脚本 `chmod +x` / `git add`+`git commit`+`git push`）**自动执行**；② GUI 类环境自适应（交互终端自动执行、无头跳过不阻塞）；③ 保留确认类（改用户级配置 / **破坏性** git 操作（`push --force`、删分支）/ 目标项目与 `{output_dir}` 外写盘 / 用户专属动作）交互式停下问，**无头经 `diyc.py defer-add` 入队 `deferred-actions.yaml` 不阻塞**。详见 §七「副作用纪律」 |

**读取成本纪律的适用范围**：不止新技能——**现有 14 个技能按同一纪律回改**（排入阶段 C；批次 4「写作块压缩」已于 2026-09-13 完成，同改一批 SKILL.md 的排序约束已满足）。

**确定性下沉原则**：BMAD 原技能里能确定性计算的部分（校验、解析、清单生成）一律下沉到 `scripts/*.py`，不留给 LLM。**现成载体 = `diy-tools`（diyc，9 子命令）**：实例解析走 `resolve`、终门走 `check`、追溯走 `trace`、状态写回走 `transition/green/done`——新技能一律接 diyc，不另起脚本；接线句照抄 `diy-coder/.analysis/2026-09-13-cross-skill/batch3-contract.md` §8 模板（2026-09-13 裁定）。

## 三、关键杠杆：全景图数据即迁移蓝图

`docs/bmad-skill-map/raw/skill-map.json` 每条技能已含 `phase / precededBy / followedBy / required / args / outputLocation / outputs / menu / steps / skillDir`。迁移时直接复用，**不需要重新调研 BMAD 技能内容**：

- `steps` → diy 版 Workflow 段落的内容蓝本
- `menu` → 技能内可选分支（diy 侧可保留为 Workflow 内的分支条件）
- `dependencies` → 验收项 #8 的登记元数据 + diy-help 导航表
- `skillDir` → 原文件位置，改造成 diy 版时逐条对照

**这条决定了本次迁移是"有据可依的改写"而非"凭空创作"。**

## 四、必须先解决的架构缺口

迁移会撞上三个现有架构装不下的问题，必须在批次开工前定论：

### 缺口 1：diy-help 承载力（14 → 48 技能 + 双线导航）
现状：diy-help 靠产物存在性检测 + 内置推荐逻辑做动态导航，技能少时可用。
方案：改为**登记表驱动** —— 每个技能在自己的 frontmatter 或独立登记文件里声明 `phase / precededBy / followedBy / required / 产物路径 / line`，diy-help 读表推荐，不再硬编码。这张表的数据直接来自全景图（WDS 线技能的依赖链从各自 workflow 的 flow 定义继承）。

**覆盖范围（2026-09-13 校正）**：登记表覆盖 14 个存量技能（含批次 2/3 新增 `diy-augment` / `diy-tools`）+ 34 个新建 = 48，并给内部技能留「不参与推荐」口径（`diy-tools` 非用户直调；`diy-augment` 由 runner 按 done 触发）——diy-help 跳过推荐，runner 编排不受影响。

**双线导航机制**（用户拍板：WDS 线要能在 diy-help 里被导航、被 runner 编排、被 viewer 渲染）：

| 机制 | 规则 |
| --- | --- |
| 起手分叉 | 无任何产物 → 按用途问一句：产品/应用 → diy-prd；官网/营销站 → diy-wds-brief；分析/迁移现有系统 → diy-reverse（入口技能，2026-09-13 改判独立）。有产物 → 按产物存在性判定当前线 |
| 线内推荐 | 登记表 `line: mainline \| wds`；各自只推本线下一步 |
| 设计交汇点 | diy-design 双源输入，两条线在此汇合，产物三件套形态统一 |
| 后续分叉 | 设计之后：有 sprint.yaml/test-plan.yaml → 主线（diy-epics-stories→…）；仅 WDS 产物 → WDS 线（diy-dev WDS 模式 → diy-wds-evolution；如需可插架构桥） |
| 双线并存 | 检测到两条线产物同时存在时给出提示（不自动合并），由用户选定当前工作线 |
| runner/viewer | 不区分线：runner 按登记表依赖编排；viewer 按产物类型渲染（缺口 2 的通用降级覆盖所有 WDS 产物） |

### 缺口 2：viewer 产物类型
现状：viewer 只认 prd / architecture / epics / stories / test-plan / sprint / bug-log / design / openapi 九类。
新技能会引入全新产物（调研报告、UX 规格、测试架构、叙事框架、创意简报…）。
方案：**通用降级渲染**（未知文档类型走 键值+列表 的通用卡片），特殊类型按需加专属视图。避免每加一个技能就改一次 viewer。

### 缺口 3：agent 人设类怎么迁（**已定：方案 B**，2026-09-13 用户拍板）

**实测清单（逐目录核查）**：人设型技能 **16 条**——bmm 6（analyst / pm / architect / dev / ux-designer / tech-writer）、cis 6（brainstorming-coach / creative-problem-solver / design-thinking-coach / innovation-strategist / presentation-master / storyteller）、wds 3（freya-ux / saga-analyst / mimir-builder）、tea 1（bmad-tea / Murat）。判据：含完整 8 步激活 + "Do not break character" 类持续性指令、菜单指向其他技能。此前"19 条"口径偏大（误含 `bmad-agent-builder` 这类工具型技能），已修正。

**人设的真实结构（实证：Amelia / Murat）**：它自己**不实现任何能力**，是一层"人设 + 菜单"的会话级包装器。激活流程 8 步中，「干活」那一步是**派发到菜单项指向的另一个技能**。以 Amelia（agent-dev）为例，8 个菜单全部指向其他技能：

| 菜单码 | 指向技能 | diy 侧现状 |
| --- | --- | --- |
| DS | `bmad-dev-story` | ✅ diy-dev 已覆盖 |
| CR | `bmad-code-review` | ✅ diy-review 已覆盖 |
| SP | `bmad-sprint-planning` | ✅ diy-sprint 已覆盖 |
| CS | `bmad-create-story` | ❌ B2 批待迁 |
| QD | `bmad-quick-dev` | ❌ B2 批待迁 |
| QA | `bmad-qa-generate-e2e-tests` | ❌ B2 批待迁 |
| ER | `bmad-retrospective` | ❌ B2 批待迁 |
| IN | `bmad-investigate` | ❌ B2 批待迁 |

**人设的实际作用只有三条**：聚合入口（记角色不记技能名）、输出风格约束（`communication_style` 等对模型的输出行为指令）、上下文持续携带（`persistent_facts` 自动加载）。

**方案 A（否决）**：逐条迁移建 16 个 `diy-agent-*` 技能。三项验收标准直接过不了——#2 无产物 schema（人设不产出 YAML）、#3 无前置门禁（任何时候可激活，不是工作流一环）、#7 无可测契约（"是否保持风格"无确定性断言）。菜单表还是 N×M 重复引用（违反 DRY）；且在 runner 无头编排场景下人设功能被架空。

**方案 B（采用）**：不建角色技能，三个价值各自归位——

| 人设职责 | 归宿 | 状态 |
| --- | --- | --- |
| 聚合入口 | `diy-help` 登记表驱动推荐 | 缺口 1 本就必须做 |
| 输出风格约束 | 并入对应技能 SKILL.md 的 Rules 段 | 随各技能迁移时一并写 |
| 上下文持续携带 | `diy-coder.yaml` + 产物文件 | 已有 |

**决策依据**：① 人设无独有能力——菜单指向的技能本来就在迁移计划内；② 剩余价值有更好归宿——48 技能规模下"记忆角色名"的聚合路线不可行，diy-help 查表不需要记忆；风格落 SKILL.md 是每次全量重新注入，比人设"注入一次靠模型记着"更稳；③ 已有先例——`create-prd / edit-prd / validate-prd` 三条 BMAD 技能已被 `diy-prd` 一条吸收（Create/Update 双模式 + 校验内建），"技能内模式"代替"技能拆分"是 diy 既有做法；④ 成本差一个量级——16 个目录 + 多点菜单同步 vs 0 目录 + 若干风格句子。

**批次影响**（定稿口径：B1-B7，B8 取消后的净效果）：人设条目不占任何批次；合并后的 B1-B7 技能数见第五节批次表。

### 已定补充：修订历史留痕（revisions 段，2026-09-13 用户拍板）

Update 模式改完后，在产物 YAML 顶层追加一条修订记录（单一源，不另建 changelog 文件）：

```yaml
revisions:
  - date: YYYY-MM-DD
    change: FR-2.1 优先级 must → should
    reason: 用户确认首版不做实时同步
```

- 定稿后仍可改，不封存；`reason` 取自用户的 change signal
- viewer 渲染为默认折叠的"修订历史"卡片（沿用 detail 折叠做法）
- **落地节奏**：schema 起点做 `diy-prd` 样板（不碰共享文件，P 阶段后即可）；viewer 渲染涉及 `viewer.py`，按共享文件纪律排入阶段 C
- 否决的替代：独立 changelog 文件（违反单一源，必然对齐漂移）；靠 git diff（记录不了"为什么改"，非技术读者不可读）

### 已定补充：技能合并与剔除清单（2026-09-13 用户拍板[ab都采纳]）

**合并判据三问**：产物同构性（合并后是同一 YAML 的字段吗） / 变更理由共享（改动原因是否同源） / 状态所有权重叠（状态流转是否指向同一批 ID）。三问中两问为「是」即合并。

**A 级合并（5 组，同产物位、天然一体）**：

| # | 合并前 | 合并后技能 | 依据 |
| --- | --- | --- | --- |
| 1 | market-research + technical-research + domain-research | `diy-research` | 三份研究报告同构为 `research.yaml`（维度字段区分）；都是 diy-prd 的上游输入 |
| 2 | editorial-review-prose + editorial-review-structure | `diy-editorial-review` | 同一份文稿的两个透镜；一次评审出一份 findings |
| 3 | agent-builder + workflow-builder | `diy-bmb-builder` | 同一家族构建能力，产出同为构建规格 |

### 人工审核点设计

**驱动方式**：本计划不走 diy 自身的规划链（prd → architecture → stories → sprint → build-loop），因为 diy 体系当前正在改动中。改为**按本文件手工驱动、分批派 team**。
